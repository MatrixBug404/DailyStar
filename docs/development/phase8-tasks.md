# Phase 8 Implementation Tasks

**Status:** APPROVED FOR IMPLEMENTATION
**Date:** 2026-10-24
**Source:** `phase8-technical-spec-v1.0.md`
**Baseline:** `bfeeb0f251255b8eafee2ea94d7c8cb1b867d5dd`

This document defines six independently verifiable milestones for Phase 8 (Notifications). Phase 8 has been approved for implementation using the recommended defaults, accepted concurrency limitations, and authorized M1. M4 is the only milestone that modifies a locked service (`WorkflowService`); everything else is additive.

---

## Milestone Overview

| Milestone | Name | Depends on | Primary risk |
|---|---|---|---|
| M1 | Schema and migration | — | Migration safety |
| M2 | Notifications API | M1 | Authorization/scoping |
| M3 | Email delivery provider | M1 | Offline test safety, secret handling |
| M4 | WorkflowService integration | M2, M3 | Transaction side effects on a locked service |
| M5 | CMS in-app UI | M2 | UI regression in the protected shell |
| M6 | Acceptance and hardening | M1–M5 | Non-regression breadth |

Each milestone must be independently green (tests, typecheck, build) before the next begins. M2 and M3 may run in parallel after M1 if staffed; M4 requires both.

## M3 — Email Delivery Provider and Pipeline

**Deliverables**
- `EmailProvider` interface + `EMAIL_PROVIDER` token.
- `LogEmailProvider` (default) and `PostmarkEmailProvider` (native `fetch`, redacted errors, timeout).
- Provider factory with startup validation.
- `notification-email` BullMQ queue registration + `NotificationEmailProcessor`.
- `EmailDispatchService` (post-commit enqueue, jobId = notification.id, conditional `SKIPPED` handling, enqueue-failure logging).
- `NotificationEmailReconciler` (`@Cron(EVERY_5_MINUTES)`, config-gated, bounded): implements spec §8.2 precedence, crash recovery, live-job deferral, and compare-and-set transitions; sole authority for `FAILED` after an eligible delivery exhausts its retry/recovery policy.
- Configuration additions + `.env.example` placeholders.

**Files (new)**
- `apps/api/src/modules/notifications/email/email-provider.interface.ts`
- `apps/api/src/modules/notifications/email/log-email.provider.ts`
- `apps/api/src/modules/notifications/email/postmark-email.provider.ts`
- `apps/api/src/modules/notifications/email/email-dispatch.service.ts`
- `apps/api/src/modules/notifications/email/notification-email.processor.ts`
- `apps/api/src/modules/notifications/email/notification-email.reconciler.ts`
- Corresponding `.spec.ts` files.

**Files (modified)**
- `apps/api/src/config/configuration.ts` (notifications/email section)
- `.env.example` (placeholders only)
- `apps/api/src/modules/notifications/notifications.module.ts`

**Design references:** spec §8, §9.

**Acceptance criteria**
- AC-6, AC-11, AC-12, AC-17 pass.
- No outbound network call in tests or CI; provider is injectable and mocked.
- `EMAIL_PROVIDER=postmark` without a token fails startup with a clear message.
- Token never appears in logs, errors, fixtures, or API output.
- Queue retries use exponential backoff; jobId is the notification ID.
- Reconciler follows spec §8.2 precedence: completed → `SENT` (CAS, no resend); observed live jobs left `PENDING` and untouched; exhausted-failed → `SKIPPED` (ineligible) or `FAILED` (eligible); missing → enqueue (eligible, attempts remaining), `SKIPPED` (ineligible), or `FAILED` (eligible, attempts exhausted); Redis inconclusive leaves `PENDING` with no attempt increment; the commit-before-enqueue crash is recovered once Redis is available.
- All delivery-state writes are CAS from `PENDING`; terminal `SENT`/`SKIPPED`/`FAILED` are immutable; the worker re-checks immediately before send; the sweep never writes a terminal state for an observed live job; the residual stale-observation window is documented in spec §8.3.

**Tests**
- Unit: provider factory, log provider, Postmark adapter with mocked `fetch` (2xx, 4xx, 5xx, timeout, token redaction).
- Unit: dispatch (PENDING only, inactive/no-email `SKIPPED`, enqueue failure caught), processor (success/failure/idempotency; terminal `SENT`/`SKIPPED`/`FAILED` no-op; pre-send status/recipient re-check; zero-match conditional does not overwrite), reconciler (completed → conditional `SENT`; live waiting/delayed/active/retrying → no status mutation even if the recipient is inactive; exhausted eligible → `FAILED`; exhausted ineligible → `SKIPPED`; missing inactive/no-email → `SKIPPED`; missing eligible with attempts remaining → enqueue; missing eligible with attempts exhausted → `FAILED`; Redis unavailable/inconclusive → remains `PENDING` with no attempt increment; zero-match conditional does not overwrite).
- Integration: enqueue a notification row and process it with a fake provider; assert `SENT`; simulate enqueue failure and verify the sweep repairs; simulate retry exhaustion and verify `FAILED`; simulate crash-before-enqueue then deactivate the recipient or remove the email address, and verify the sweep marks `SKIPPED` (not `PENDING`) with no email sent.
- Concurrency: block the fake provider mid-send, deactivate the recipient, run the sweep while the job is observed active, and assert the row remains `PENDING` with the job untouched; release the send → `SENT`; assert pre-send deactivation → `SKIPPED` with no provider call, and stale reconciliation after `SENT`/`SKIPPED` cannot overwrite the terminal state.

**Rollback / failure handling**
- Set `EMAIL_PROVIDER=log` to disable external delivery without code changes.
- Disable the reconciler via `EMAIL_RECONCILE_ENABLED=false` if it misbehaves.
- Removing the queue registration and processor reverts to API-only notifications; rows remain valid.

**Exit gate:** delivery pipeline green with no triggers wired (queue naturally empty).

## Cross-Milestone Dependency Notes

- **No circular module dependency:** `WorkflowModule → NotificationsModule` is one-way. `NotificationsModule` must never import `WorkflowModule`; recipient/event data is passed in.
- **`forwardRef` is not expected:** the existing `WorkflowModule ↔ SchedulingModule` cycle is unrelated. If a cycle appears, stop and report rather than adding `forwardRef` reflexively.
- **Queue registration:** `notification-email` uses the global Bull root config; do not create a second Redis connection factory.
- **Prisma client generation:** CI already runs `prisma:generate` in lint/typecheck/test jobs and the API build script generates the client; the new model is covered automatically.
- **Environment:** local Docker stack (Postgres/Redis/MinIO) is sufficient; no mail container is required for M1–M6.
